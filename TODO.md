### M2 — Remote hosts

- `SshHost` assumes a GNU `find` on the remote (uses `-printf '%T@ %p\0'`). macOS remotes need Homebrew `findutils` or a BSD-stat fallback. Defer until a macOS remote actually surfaces. `#m2 #remote #portability`
- remote polling: surface persistent `list_transcripts` failures (e.g. SSH master died mid-run) instead of silently retrying every tick. Today the polling loop swallows errors so attention freezes silently when a host goes away. Likely shape: an `AttentionUpdate(_, Unknown)` for every known session on the affected host after N consecutive failures, plus a footer hint mirroring the startup `connect_errors` line. Defer until dogfooding shows it's actually a problem — for stable home-LAN SSH the silent retry is often fine. `#m2 #remote #attention`
- remote polling: known-set never shrinks. When a transcript is deleted on the remote, the polling thread's `HashMap` keeps the entry forever and the catalog keeps a stale row. Probably wants to be addressed together with deletion handling in the catalog (no current code path removes sessions). Defer until session-removal is on the menu. `#m2 #remote #lifecycle`
- remote attach: nested-tmux prefix collision when running agent-mux from inside local tmux. Documented as a known gotcha in README; users handle it with a different inner-tmux prefix or `<prefix> <prefix>` passthrough. Revisit if dogfooding shows it's worse than expected — possible mitigations: pin the remote tmux to a separate socket name we could later override config on, or wrap with byobu. `#m2 #remote #ux`
- remote attach: the auto-spawned `agent-mux-<id>` tmux sessions on the remote accumulate over time — every resumed conversation leaves one behind. The user can `tmux kill-session` manually; a discard/cleanup affordance from the dashboard would be nicer. Plausibly bundles with the post-M4 worktree discard/merge workflow. `#m2 #remote #cleanup`
- dashboard: indicate per-row whether a session has a live tmux pane (i.e. Enter will be a fast switch vs. an auto-resume). Mechanism: periodic `tmux list-panes -a -F '... #{pane_current_path}'` (locally for local sessions, over each host's existing ControlMaster for remote), intersected with the catalog's project_dirs, stored as a per-session boolean. Piggyback on the 3s remote-attention poller so we don't add a second cadence; same shape for the local case. Visual: probably dim the title when no live pane — cheapest option, no new glyph, semantic of "dormant — attach will resume from disk." Race against pane death between indicator and Enter is fine (the auto-resume fallback handles it gracefully — the indicator is a hint). Could be done now or bundled with M3 inline preview, where the row will show more per-session state anyway. Reason it's worth doing: lets the user pre-mentally-model attach cost (fast switch vs. spin up tmux + claude), and surfaces accumulated `agent-mux-<id>` cruft on remotes. `#dashboard #ux #m2-or-m3`
- cache historical remote sessions to disk so the dashboard renders them immediately on startup instead of waiting for each host's SSH connect to complete. Today, local sessions appear instantly but remote rows pop in over multiple seconds as each `ControlMaster` handshake finishes — annoying when most of the user's work lives on one or two remote hosts. Mechanism: after a successful remote discovery, write a per-host snapshot to `~/.cache/agent-mux/sessions/<host>.json` (session id, project_dir, last_activity, title, last-observed attention). On next startup, populate the catalog from cache immediately, then refresh asynchronously when the live connect succeeds — drop entries not in live results, update the rest. Visual question to settle at implementation: do cached rows look different from live ones until refreshed (e.g. an extra dim modifier), or do we trust the cache enough to render normally? The latter is cheaper to implement; the former is safer against acting on stale data. Defer the answer to implementation time. `#m2 #remote #startup #ux`

- post-M2: switch-latency smoke test (or criterion benchmark) that fails if a focus-change round trip exceeds a budget (target: ≤ 50ms against an in-memory catalog populated with N sessions). Reason: claude-squad's 10+ second switching is the empirical failure mode we exist to avoid. Deferred from M0 — the budget needs to cover both local and remote switching, and setting a local-only number now risks rework once M2 lands. `#post-m2 #perf`
- bound discovery memory: `Host::read_to_string` currently allocates the full transcript for cwd/title extraction at startup. For multi-MB transcripts × N sessions this is a real transient spike, and over SSH it's a per-session round-trip of the whole file. Likely fix: cap discovery reads to head (e.g. first 64 KB for cwd + first-user-message) + tail (e.g. last 32 KB for the latest `ai-title`); add a `read_head` companion to `read_tail` on the `Host` trait, both bounded. Deferred — wait for SSH-impl dogfooding to confirm the memory/latency cost is real before adding trait surface. `#post-m2 #perf #host`
- OS-level attention notifications when a session transitions into `needs-input`. Promised in `SPEC.md` ("(eventually) the user receives an OS-level notification") but not pinned to any milestone — this entry exists to close that gap. Mechanism: cross-platform via the `notify-rust` crate (libnotify on Linux, NSUserNotification on macOS). Trigger at the catalog's attention-update boundary: when the *previous* attention was `Working`/`Idle`/`Unknown` and the *new* attention is `NeedsInput`, fire one notification with the session's title + host label so the user knows where to look. Suppression to settle at implementation time: don't notify when agent-mux's terminal has focus (if reliably detectable across terminal emulators — may not be), debounce against rapid attention flapping, and likely a per-session "I've seen this, hush" so we don't re-notify on every transition while the user is mid-decision. Config knobs (on/off, sound, quiet hours, per-host suppression) belong in M4. Roadmap placement: natural to bundle with M3 (both surface session state more richly), but could also stand alone between M3 and M4. Decide at the time. `#notifications #m3-bundle-or-own`
- shutdown cleanup audit: what tmux/SSH state does agent-mux own across its lifecycle, and what survives a normal quit (q/Ctrl-C), a SIGTERM, and a panic? Catalog candidates: (a) the SSH `ControlMaster` sockets per remote — `SshHost::Drop` runs `ssh -O exit` and `ControlPersist=600` is a belt-and-braces, but a SIGKILL or panic during unwind may leave the socket on disk for up to 10 min; (b) the local tmux windows that hold `ssh -t target tmux attach` for a remote attach — these self-close when ssh exits (default `remain-on-exit off`), but the user's tmux config could keep them around; (c) the remote `agent-mux-<conv-id>` tmux sessions — these are deliberately persistent for idempotent re-attach, *not* something to clean up automatically (filed separately as `#m2 #remote #cleanup`); (d) background threads (transcript watcher, per-host polling) — these exit cleanly when the event channel drops, but worth verifying nothing leaks under panic. Audit goal: confirm each scenario above behaves as intended, add an integration test where feasible, and document the deliberate-persistence vs. cleanup distinctions so future contributors don't accidentally "fix" what's intentional. Plausibly bundles with the post-M4 discard/cleanup workflow when we also add user-facing affordances to remove things. `#cleanup #lifecycle #audit`
