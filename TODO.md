- stray newline / garbage in Claude prompt on session swap — defensive fix landed 2026-05-20 (the leader-armed Esc transition ignores stray modifier bits), then re-opened 2026-05-28 after dogfooding still saw it. A one-shot env-gated byte logger (`MUX_KEYLOG`) captured the actual sequence: an SGR mouse report (`\x1b[<35;49;59M`) was decomposed by `crossterm` into 14 individual `KeyEvent`s with ~10–11 ms inter-byte gaps, and our `handle_terminal_key` faithfully forwarded each byte to the embedded PTY. Claude then received `\e\e\e[<35;49;59M` as keystrokes, leaking literal `[<…M` (or, perceptually, "stray characters / a newline") into the prompt buffer. Subsequent mouse reports in the same burst parsed correctly as `Event::Mouse`, so the failure is the *first* report after a quiescent stretch — likely crossterm's CSI parser timing out between the leading `Esc` and the rest of the sequence when the OS/terminal delivers the bytes slowly. Two candidate fixes:
  - **(1) Filter at the handler boundary.** In `Focus::Terminal`, buffer a bare `Esc` for up to ~30 ms before forwarding. If a `[` follows within the window, hold both. If a parameter byte (`<`, digit, `;`) follows, treat as a misparsed CSI and suppress everything until the terminator (any byte in 0x40–0x7E). Otherwise flush the held bytes and forward normally. Cost: ~30 ms latency on bare-Esc presses; structurally cleaner than a per-byte filter and contained to one module. Lowest risk.
  - **(2) Bypass crossterm's parser for terminal-focus input.** Read raw stdin bytes ourselves while `Focus::Terminal`, split off only the `Ctrl-a Esc` leader chord, pipe everything else straight to the PTY. Fixes the entire class of bug structurally (mouse, keyboard, future protocols all pass through unchanged) but touches the event loop in fundamental ways — higher engineering cost, broader blast radius. Worth reaching for if (1) leaves residue.
  Also flagged in the same log: two unprompted Ctrl-D events after another swap (lines 221, 224 of `stray_newlines_investigation.log`). Could be the user's own keystrokes or a parallel symptom of the same misparsing — re-check after the fix lands. `#embedded-pty #dogfood`
- two SessionIds collapsing onto one tmux pane (dogfooded 2026-05-28). `tmux list-sessions` showed `agent-mux-b540…` (a session agent-mux created via `tmux_resume_argv`) plus an externally-created session named `3`; the sidebar had a second row for `fcd6…` (an externally-started Claude conversation) with no `agent-mux-fcd6…` tmux session of its own. `resolve_pane_target` correctly pins `b540` to its own `agent-mux-<id>` session, but `fcd6` falls through to the cwd-matching fallback (the "externally-created sessions and never-re-attached agent-mux sessions" branch in ARCHITECTURE.md) and the first matching pane it finds is `agent-mux-b540…:0.0` — same cwd. Both rows then route Enter through the same `tmux attach -t agent-mux-b540…:0.0` argv. Concrete consequence: swapping between the two rows drops the existing `tmux attach` PTY and respawns a fresh one against the same pane (SIGHUP → tmux client detach → fresh client connect → resize storm as the new PTY moves from 24×80 to the real pane dimensions), which is gratuitous churn at best and possibly the actual mechanism behind the "stray newline on swap" repro above (SIGWINCH burst → Claude prompt re-wraps with a literal `\n` inserted at the wrap point). Two plausible fixes: (a) when the new and old `EmbedSpec` resolve to identical argv, take the same fast path `install_embedded` uses for "same SessionId" — keep the PTY, just retarget focus; (b) extend `resolve_pane_target`'s cwd fallback so an externally-started Claude that lacks an `agent-mux-<id>` session gets its OWN unique tmux session on first attach, rather than piggybacking on an unrelated row's. (a) closes the immediate churn; (b) fixes the deeper "two sidebar rows secretly share state" surprise. `#embedded-pty #attachment #dogfood`
- garbled text on remote-session load (dogfooded 2026-05-21): at least one time when swapping into a remote session, the embedded PTY rendered jumbled/corrupted output as if the previous frame wasn't fully cleared before the new session's content arrived. Hypothesis: on swap we hand off the pane to the new session's PTY without resetting the terminal state (cursor position, SGR attributes, alt-screen, scroll region), so the first burst of bytes from the new session is interpreted against the previous session's lingering state. Possible reproduction-aiding moves: (a) emit a full reset (`\x1bc` or `\x1b[!p` + `\x1b[?1049l` + `\x1b[0m` + clear) into the pane at swap time before piping the new session through; (b) capture a one-shot byte log of the first ~4 KB the new session writes after swap, behind an env var, to see whether the corruption is on our side (stale state) or the remote's first bytes (e.g. partial CSI mid-sequence from a buffered read). Defer chasing until there's a second sighting or the byte log gives us a clue — single-occurrence visual glitches over SSH have many possible causes (proxy hiccup, mid-frame redraw race). `#embedded-pty #remote #dogfood`

### Discovery & catalog perf

- subagent (sidechain) transcript filter — content-marker fallback. The path-shape filter shipped 2026-05-27 (local notify thread rejects transcripts whose grandparent isn't the projects root, mirroring the depth-2 shape `Host::list_transcripts` already enforces) closes the immediate noise: Claude Code's `Task`-spawned subagents write at `<bucket>/<parent-session-id>/subagents/agent-<id>.jsonl`, which the recursive `notify` watch otherwise surfaced as standalone flapping rows. The path-shape signal is coupled to Claude Code's current on-disk layout; if a future release flattens subagents back to `<bucket>/agent-<id>.jsonl`, the filter would silently miss them. The content-marker hedge: every entry in a subagent transcript carries `"isSidechain": true` (plus an `"agentId"` field) on the very first line — a sub-millisecond partial read from a page-cache-hot file at `NewTranscript` time would catch the case the path filter misses. Defer until / unless Claude Code changes the layout; if it does, the move is to add the check at the watcher's `NewTranscript` fork and keep the path filter as the fast pre-check. `#discovery #attention`
- decide session discovery policy: all-transcripts vs recent-only vs explicit-register vs hybrid. **2026-05-18:** dogfooding surfaced this — 233 stale transcripts on a long-lived remote box, see the remote-discovery optimisation arc under Remote hosts for measured numbers. The recent-only option is now the leading candidate because it composes cleanly with that work. `#discovery`
- bound discovery memory: `Host::read_to_string` currently allocates the full transcript for cwd/title extraction at startup. For multi-MB transcripts × N sessions this is a real transient spike, and over SSH it's a per-session round-trip of the whole file. Likely fix: cap discovery reads to head (e.g. first 64 KB for cwd + first-user-message) + tail (e.g. last 32 KB for the latest `ai-title`); add a `read_head` companion to `read_tail` on the `Host` trait, both bounded. Deferred — wait for SSH-impl dogfooding to confirm the memory/latency cost is real before adding trait surface. `#perf #host`
- switch-latency smoke test (or criterion benchmark) that fails if a focus-change round trip exceeds a budget (target: ≤ 50ms against an in-memory catalog populated with N sessions). Reason: claude-squad's 10+ second switching is the empirical failure mode we exist to avoid. The budget needs to cover both local and remote switching. `#perf`
