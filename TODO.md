- per-host `multiplex = false` opt-out for proxies that can't sustain a `-fN -M` master. Follow-up to the 2026-05-27 verify-after-spawn fix that turned silent degradation into a loud `connect_errors` line: a user whose ProxyCommand can't keep a backgrounded ControlMaster alive (Coder `coder ssh --stdio` gated by a `Match host *.coder !exec "coder connect exists %h"` rule was the original repro) now sees the host fail to connect at startup instead of paying silent per-command SSH cost. That's the right default — it preserves "session switching never blocks on I/O" by refusing to register a host that would violate it. But it also leaves that user with no working remote at all until they either fix their SSH config or formalize the unmultiplexed path. A `[hosts.<name>].multiplex = false` config knob would let the user opt into per-command SSH for that host explicitly: skip the `-fN -M` master spawn at connect time, drop the `-S <control_path>` arg from `ssh_command()` / `ssh_argv()`, and accept the per-operation handshake as the documented mode. Wait to ship until dogfooding tells us whether a real user actually hits the new failure surface and needs the opt-out — the loud-failure UX may turn out to be enough on its own (user fixes the SSH config or removes the host). When it does ship, the design call is whether to emit a one-time startup warning ("host X is in unmultiplexed mode; session switching will block on I/O") so the architectural compromise stays visible rather than becoming a quiet escape valve from the load-bearing property. `#remote #reliability #config #ssh #dogfood`
- dead `ControlMaster` reconnect — remaining follow-up (core reconnect 2026-06-23; backoff + pane-poller gating 2026-06-24, see FEATURES.md). **Backoff (was #2) and pane-poller gating (was #3) shipped** after dogfooding surfaced the storm they were filed to prevent: on a host whose master *can't* be re-established (the user's Coder-proxied remote, which can't sustain `-fN -M`), the un-throttled reconnect re-spawned a doomed `ssh -fN -M` (≈5 s `ConnectTimeout`) every 3 s tick from the transcript poller *and* the pane poller fired a fresh `ssh tmux list-panes` on the dead socket each tick — surfacing as a burst of short-lived ssh processes (the user saw "a bunch of tmux windows running ssh, no output, gone in 5–10 s"). - stray newline / garbage in Claude prompt on session swap — defensive fix landed 2026-05-20 (the leader-armed Esc transition ignores stray modifier bits), then re-opened 2026-05-28 after dogfooding still saw it. A one-shot env-gated byte logger (`MUX_KEYLOG`) captured the actual sequence: an SGR mouse report (`\x1b[<35;49;59M`) was decomposed by `crossterm` into 14 individual `KeyEvent`s with ~10–11 ms inter-byte gaps, and our `handle_terminal_key` faithfully forwarded each byte to the embedded PTY. Claude then received `\e\e\e[<35;49;59M` as keystrokes, leaking literal `[<…M` (or, perceptually, "stray characters / a newline") into the prompt buffer. Subsequent mouse reports in the same burst parsed correctly as `Event::Mouse`, so the failure is the *first* report after a quiescent stretch — likely crossterm's CSI parser timing out between the leading `Esc` and the rest of the sequence when the OS/terminal delivers the bytes slowly. Two candidate fixes:
  - **(1) Filter at the handler boundary.** In `Focus::Terminal`, buffer a bare `Esc` for up to ~30 ms before forwarding. If a `[` follows within the window, hold both. If a parameter byte (`<`, digit, `;`) follows, treat as a misparsed CSI and suppress everything until the terminator (any byte in 0x40–0x7E). Otherwise flush the held bytes and forward normally. Cost: ~30 ms latency on bare-Esc presses; structurally cleaner than a per-byte filter and contained to one module. Lowest risk.
  - **(2) Bypass crossterm's parser for terminal-focus input.** Read raw stdin bytes ourselves while `Focus::Terminal`, split off only the `Ctrl-a Esc` leader chord, pipe everything else straight to the PTY. Fixes the entire class of bug structurally (mouse, keyboard, future protocols all pass through unchanged) but touches the event loop in fundamental ways — higher engineering cost, broader blast radius. Worth reaching for if (1) leaves residue.
  Also flagged in the same log: two unprompted Ctrl-D events after another swap (lines 221, 224 of `stray_newlines_investigation.log`). Could be the user's own keystrokes or a parallel symptom of the same misparsing — re-check after the fix lands. `#embedded-pty #dogfood`
- externally-started sessions sharing one cwd still collide on the pane cwd-fallback. The agent-mux-spawned case is **fixed** (2026-07-07, see FEATURES.md — spawned sessions now carry the id-derived `agent-mux-<uuid>` tmux name via `claude --session-id`, so `resolve_pane_target` stage 1 pins them). What remains: two sessions the user started *outside* agent-mux in the same directory (e.g. `claude` run by hand twice) have no `agent-mux-<id>` name and we can't inject one at discovery, so both rows resolve to the first cwd-matching pane and selecting either opens whichever sorts first. Fix shape: transcript→pane process matching — `lsof -t <transcript>` gives the writer PID (`probe_live_writer` already shells this for the resume gate), then map it to the owning tmux pane via `#{pane_pid}` (direct match when `claude` is the pane's process, else a bounded parent-PID walk; macOS `ps -o ppid=` vs Linux `/proc`). Runs on the attach hot path, so measure — but attach already does `tmux list-panes` + lsof, so the marginal cost is one more field + a short walk. Remote needs remote `lsof` (pairs with the deferred remote parallel-resume probe). Deferred until an externally-started-dupe sighting actually bites; the reported pain (agent-mux-spawned no-worktree sessions) is resolved. `#embedded-pty #attachment`
- garbled text on remote-session load (dogfooded 2026-05-21): at least one time when swapping into a remote session, the embedded PTY rendered jumbled/corrupted output as if the previous frame wasn't fully cleared before the new session's content arrived. Hypothesis: on swap we hand off the pane to the new session's PTY without resetting the terminal state (cursor position, SGR attributes, alt-screen, scroll region), so the first burst of bytes from the new session is interpreted against the previous session's lingering state. Possible reproduction-aiding moves: (a) emit a full reset (`\x1bc` or `\x1b[!p` + `\x1b[?1049l` + `\x1b[0m` + clear) into the pane at swap time before piping the new session through; (b) capture a one-shot byte log of the first ~4 KB the new session writes after swap, behind an env var, to see whether the corruption is on our side (stale state) or the remote's first bytes (e.g. partial CSI mid-sequence from a buffered read). Defer chasing until there's a second sighting or the byte log gives us a clue — single-occurrence visual glitches over SSH have many possible causes (proxy hiccup, mid-frame redraw race). `#embedded-pty #remote #dogfood`
