- remote polling: surface persistent `list_transcripts` failures (e.g. SSH master died mid-run) instead of silently retrying every tick. Today the polling loop swallows errors so attention freezes silently when a host goes away. Likely shape: an `AttentionUpdate(_, Unknown)` for every known session on the affected host after N consecutive failures, plus a footer hint mirroring the startup `connect_errors` line. Defer until dogfooding shows it's actually a problem — for stable home-LAN SSH the silent retry is often fine. `#attention #remote`
- terminal-focus suppression (don't notify when agent-mux's terminal already has focus): defer to dogfooding — likely not reliably detectable across terminal emulators, and may not be worth special-casing if it turns out rare in practice. `#notifications #dogfood`
- WSL2 dogfooding: confirm notifications surface on the user's WSL2 + WSLg setup. `notify-rust` uses D-Bus on Linux; WSLg ships a notification daemon but variability across distros is real. If notifications don't appear, document the workaround (or pin a different backend) rather than silently failing. `#notifications #dogfood`
- bell-style notification fallback for hosts where the OS path is dead (terminal bell + dashboard footer flash). Filed after the per-platform backend trait shipped 2026-05-21 — that covered macOS (`osascript`) and WSL (`wsl-notify-send.exe`) which were the immediate gaps, but there's no truly-cross-platform last resort yet. Open: the bell would need to push state back to the dashboard render loop (which the current `Dispatcher` trait doesn't surface), so this is a small refactor on top of the existing backend dispatch. Defer until dogfooding shows the three OS-specific backends still leave a real gap. `#notifications #portability`
- `Notifier::forget` wiring: when `SessionCatalog::reconcile_host` drops entries (remote session gone), the per-session suppression state in `Notifier` leaks. Each entry is ~24 bytes so it's not urgent; revisit if a long-lived process shows growth. Reconciliation would need to expose which ids were dropped. `#notifications #lifecycle #cleanup`
- quiet hours for notifications: a `[notifications]` field like `quiet_hours = ["22:00-07:00"]` to suppress dispatch during a user-defined window. Deferred because timezone-aware time parsing adds scope; the on/off toggle and per-host suppression already cover the common case. `#notifications #config`
- customizable notification sounds: today's surface exposes a single `sound = true/false` flag mapping to the OS "default" sound. Real customization would mean per-host or per-event sound selection (different sound for needs-input vs. attention-flap; one host gets a chime, another gets a buzz). Wait for dogfooding to surface whether the binary toggle is enough; revisit if not. `#notifications #config`
- Claude Code `Notification` hook as a richer attention signal — feasibility investigated 2026-05-21, deferred behind the heuristic fix that shipped the same day. Findings:
  - **`Stop` is the wrong hook.** It fires on *every* turn end, including each tool-call turn in an agentic loop. Using it for "needs input" would be worse than the heuristic.
  - **`Notification` is the right hook.** Designed to fire when the session genuinely needs user attention (permission prompts, awaiting next prompt). Payload carries `session_id`, `cwd`, `hook_event_name`, plus a matcher disambiguating the cause. Exact matcher names (`idle_prompt`, `permission_prompt`?) need verifying against current Claude Code docs before any build — the research subagent cited them but I didn't confirm against the official source.
  - **Integration shape if we pursue it.** (a) hook is a shell command run on the *machine where `claude` runs* — so local sessions need `~/.claude/settings.json` configured locally, remote sessions need it configured on each remote host; (b) hook receives JSON on stdin and is fire-and-forget; (c) agent-mux needs an ingress on the local side — simplest is a known file path the existing `notify` watcher picks up, alternatives are a unix socket or an `agent-mux notify` CLI subcommand that IPCs to the running dashboard; (d) the remote story is the awkward bit — the hook on the remote needs to reach back to local agent-mux, easiest path is "hook writes a marker file under the transcript root that the existing remote poller already polls on its 3 s tick" (re-uses the SSH connection, no extra network plumbing); (e) provisioning: either documented setup step (user edits `~/.claude/settings.json` themselves on each host) or agent-mux mutates the file automatically (which raises trust questions about touching user dotfiles on remotes); (f) the transcript-tail path stays as fallback for hosts without the hook installed, so this is hook *plus* heuristic, not hook *instead of*.
  - **Why deferred.** The heuristic fix (assistant `stop_reason == "tool_use"` → Working) addressed the dominant noise source — every tool_use no longer flickers NeedsInput. Hook integration is order-of-weeks vs order-of-hours. Revisit if dogfooding shows the heuristic still leaves real noise (e.g. assistant entries with non-tool-use stop_reasons mid-stream, or permission prompts where the model has technically ended its turn but is mid-permission-dialog).
  `#notifications #attention #hooks`

### Remote hosts

- `SshHost` assumes a GNU `find` on the remote (uses `-printf '%T@ %p\0'`). macOS remotes need Homebrew `findutils` or a BSD-stat fallback. Defer until a macOS remote actually surfaces. `#remote #portability`
- remote attach: nested-tmux prefix collision when running agent-mux from inside local tmux. Documented as a known gotcha in README; users handle it with a different inner-tmux prefix or `<prefix> <prefix>` passthrough. Revisit if dogfooding shows it's worse than expected — possible mitigations: pin the remote tmux to a separate socket name we could later override config on, or wrap with byobu. `#remote #ux`
- remote-session cache: decide whether to visually distinguish cached-but-not-yet-refreshed rows from live ones. Shipped with no distinction in 2026-05 — argument was that the cache reflects last-known state and the staleness window is bounded by the SSH handshake (~seconds). Revisit if dogfooding shows confusion ("why is this row showing stale attention?"). Lowest-cost option: extra dim modifier on rows whose host is in `pending_hosts`. `#remote #ux`
- remote-repo disk cache: the remote-session-creation arc deliberately skipped the design sketch's `~/.cache/agent-mux/repos/<host>.json` snapshot. With the in-process pipeline (Connected → background scan → reconcile_host), the picker shows remote repos within a few seconds of launch — fast enough for the warm-launch case. Cache becomes worthwhile for the cold-launch case where the user presses `n` immediately and hasn't seen the host connect yet. Mirror the session-cache pattern (`cache::repos_default_dir`, `read_repos_for_host`, `write_repos_for_host`, atomic `tmp + rename`) and seed the registry from disk at `App::new` time so the picker is instant. Defer until dogfooding shows the "press n immediately" case bites. `#remote #cache`
- remote default-branch resolution: when the picker transitions to Filling for a remote repo, the branch field starts empty rather than running `git symbolic-ref` over SSH inline (a half-second proxy round-trip mid-keypress would block the UI). The user types the branch manually. Two ways to fix: (a) resolve eagerly during the background workspace scan — adds one git invocation per remote repo at scan time, modest cost amortised over the scan, and the picker has the answer ready; (b) resolve lazily on selection change in a background thread, populate the field when it arrives. (a) is simpler. Either way needs `RepoRegistry` to carry an optional `default_branch` per Repo, plus updates to the modal to honour it. `#remote #ux`
- remote discovery on high-latency proxied SSH (Coder, jumphost) — progress log of the optimisation arc. Original measurement 2026-05-18 against coder-proxied `gizmo.coder`: 233 transcripts × 4 sequential SSH round-trips per session ≈ 7+ minutes wall-clock. Shipped same day in two passes:
  1. ~~**Filter by recency at the `find` boundary.**~~ `DISCOVERY_MAX_AGE` in `src/discovery.rs`, 30 days default. 233 → 21 surviving sessions. Brought wall-clock to 55 s. The configurable knob is tracked under Configuration.
  2. ~~**Batch per-transcript reads into one round-trip + compute attention from the same buffer (collapses option 4).**~~ Added `Host::read_many` and `Host::is_dir_many` and a `derive_attention_from_content` helper; refactored `discover()` to do list + bulk-read + bulk-is_dir + bulk-task.toml in four total SSH round-trips regardless of N, with attention falling out of the already-fetched buffers. SSH `Compression=yes` set on the `ControlMaster`. End-to-end now ~6 s warm / ~15 s cold on the same host (down from 55 s).
  3. ~~**Stream sessions into the catalog progressively.**~~ Shipped 2026-05-18 in a smaller-than-originally-scoped form. The actual user-pain wasn't "blank dashboard while discovery runs" (the cache already paints rows on first frame); it was that *cached rows weren't attachable* until discovery finished because `App.hosts` only learned about the `Arc<dyn Host>` at `Ready` time. Fix: split `RemoteDiscoveryResult` into `Connected` (fires after SSH `ControlMaster` is up, ~3 s) and `Ready` (fires after discovery, later). `Connected` registers the host + starts the polling threads, so cached rows become attachable within seconds of launch even if discovery is still grinding. Full per-session streaming into the catalog wasn't necessary for this complaint — the cache already does that part. Revisit if a *new* dogfooding signal asks for "watch rows pop in" UX.
  4. **Head-and-tail reads for transcripts.** Cold-case discovery is dominated by ~16 MB of transcript bytes streaming through the proxy. Most of that is the middle of long transcripts that discovery doesn't need (only first lines for cwd/first-user-message, last lines for ai-title/attention). A `read_head_tail_many(paths, head_bytes, tail_bytes)` op would cut payload to ~3 MB → ~2 s. Defer until dogfooding tells us whether the cold 15 s actually bites; the warm 6 s already covers the common re-launch case.
  `#remote #perf #discovery #dogfood`
- remote polling: known-set never shrinks. When a transcript is deleted on the remote, the polling thread's `HashMap` keeps the entry forever and the catalog keeps a stale row. Probably wants to be addressed together with deletion handling in the catalog (no current code path removes sessions). Defer until session-removal is on the menu. `#remote #lifecycle`
- remote attach: the auto-spawned `agent-mux-<id>` tmux sessions on the remote accumulate over time — every resumed conversation leaves one behind. The user can `tmux kill-session` manually; a discard/cleanup affordance from the dashboard would be nicer. Plausibly bundles with the worktree discard/merge workflow. `#remote #cleanup`
- remote-session cache: cleanup of orphaned `~/.cache/agent-mux/sessions/<host>.json` files when a host is removed from config. Today the file is left on disk; harmless (it's never read because we only load cache for hosts in current config) but leaks bytes. `#remote #cleanup`
- stale-socket sweep on `SshHost::connect`: when a previous agent-mux is killed mid-`thread::sleep`, its `agent-mux-ssh-<host>-<pid>.sock` file may persist in `$TMPDIR` past the remote master's `ControlPersist` window. Harmless on first principles (a fresh PID gets a fresh path so the socket file never collides with a new connect attempt) but leaks files until tmpdir cleanup. Mitigation: at connect time, list `$TMPDIR/agent-mux-ssh-*-<pid>.sock` entries whose `<pid>` is no longer a live process and remove them. Reason it's a real concern only at scale: a heavy dogfooder + monthly tmpdir rotation could leave dozens of zero-byte sockets. Filed during the 2026-05 shutdown audit. `#remote #cleanup #lifecycle`

### Embedded PTY

- embedded-PTY polish (post-Phase-6): F5+ key codes, ScrollLeft/ScrollRight mouse forwarding, terminal-focus-detection so a click into the sidebar implicitly transitions focus, a config knob for the leader chord (so users who already use `Ctrl-a` for tmux can rebind), highlight-on-hover for sidebar rows when mouse is over. Defer until dogfooding surfaces the actual pain points. `#embedded-pty #dogfood`
- in-app copy mode + OSC52 for the embedded pane. Shift+drag bypass shipped 2026-05-20 (agent-mux drops Shift-mouse events so host-terminal native selection works on iTerm2 / kitty / wezterm / Alacritty). Still open: a `<leader> y` in-app copy mode that selects in our own buffer and dispatches the selection via OSC52, for two cases the Shift bypass doesn't reach — (a) host terminals without an OS-level Shift bypass, and (b) selection over SSH where host-terminal selection lives in a remote-side buffer that can't reach the local clipboard. OSC52 likely has to be the universal answer for (b) regardless of what we do on the local side. `#embedded-pty #ux`
- stray newline on session swap — code-audit defensive fix landed 2026-05-20: the leader-armed Esc transition no longer requires `key.modifiers.is_empty()`, so Esc with stray modifier bits (Kitty Keyboard Protocol, extended event modes) still escapes back to Sidebar instead of silently leaking subsequent j/k/Enter into the inner PTY. Re-open with byte-level evidence if the repro persists after this — the next move would be a small one-shot key log behind an env var to capture the actual offending sequence (focus-event bytes, stale bracketed-paste markers, or something else entirely). `#embedded-pty #dogfood`
- garbled text on remote-session load (dogfooded 2026-05-21): at least one time when swapping into a remote session, the embedded PTY rendered jumbled/corrupted output as if the previous frame wasn't fully cleared before the new session's content arrived. Hypothesis: on swap we hand off the pane to the new session's PTY without resetting the terminal state (cursor position, SGR attributes, alt-screen, scroll region), so the first burst of bytes from the new session is interpreted against the previous session's lingering state. Possible reproduction-aiding moves: (a) emit a full reset (`\x1bc` or `\x1b[!p` + `\x1b[?1049l` + `\x1b[0m` + clear) into the pane at swap time before piping the new session through; (b) capture a one-shot byte log of the first ~4 KB the new session writes after swap, behind an env var, to see whether the corruption is on our side (stale state) or the remote's first bytes (e.g. partial CSI mid-sequence from a buffered read). Defer chasing until there's a second sighting or the byte log gives us a clue — single-occurrence visual glitches over SSH have many possible causes (proxy hiccup, mid-frame redraw race). `#embedded-pty #remote #dogfood`

### Discovery & catalog perf

- decide session discovery policy: all-transcripts vs recent-only vs explicit-register vs hybrid. **2026-05-18:** dogfooding surfaced this — 233 stale transcripts on a long-lived remote box, see the remote-discovery optimisation arc under Remote hosts for measured numbers. The recent-only option is now the leading candidate because it composes cleanly with that work. `#discovery`
- bound discovery memory: `Host::read_to_string` currently allocates the full transcript for cwd/title extraction at startup. For multi-MB transcripts × N sessions this is a real transient spike, and over SSH it's a per-session round-trip of the whole file. Likely fix: cap discovery reads to head (e.g. first 64 KB for cwd + first-user-message) + tail (e.g. last 32 KB for the latest `ai-title`); add a `read_head` companion to `read_tail` on the `Host` trait, both bounded. Deferred — wait for SSH-impl dogfooding to confirm the memory/latency cost is real before adding trait surface. `#perf #host`
- switch-latency smoke test (or criterion benchmark) that fails if a focus-change round trip exceeds a budget (target: ≤ 50ms against an in-memory catalog populated with N sessions). Reason: claude-squad's 10+ second switching is the empirical failure mode we exist to avoid. The budget needs to cover both local and remote switching. `#perf`
